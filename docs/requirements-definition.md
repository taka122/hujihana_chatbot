# 要件定義書（ドラフト）

最終更新日: 2026-02-18  
ステータス: 作成中（ユーザー案反映・仮説版）

## 0. この文書の使い方
- この文書は「一度で完成」ではなく、論点ごとに更新して精度を上げる。
- 根拠が弱い項目は「仮説」と明記する。
- 判断不能な項目は「不明」と明記し、確認先と期限を置く。
- 合意事項だけでなく、反論・代替案・懸念点を残す。

## 1. 背景・目的
### 1.1 背景
- 介護サービスを探す相談者は、地域・サービス種別・条件に合う事業所を短時間で見つけにくい。
- 事業所情報が複数ソースに分散し、比較と問い合わせ前の絞り込みに手間がかかる。
- 相談窓口側も、毎回同様の説明や候補提示を手作業で行っており工数が大きい（仮説）。

### 1.2 目的
- チャット形式で相談内容を受け取り、地域の介護事業所データに基づいて候補を提示できるRAGを構築する。
- 相談者にとって、候補探索時間を短縮し、比較に必要な最低限の情報を一度に取得できる状態を作る。
- 運営側にとって、初回案内業務の標準化と対応品質の平準化を実現する。

### 1.3 非目的（やらないこと）
- 医療・介護の診断や最終意思決定の代行は行わない。
- 契約締結、予約確定、空き枠保証は行わない。
- 全国対応や全サービス網羅は初期リリースでは行わない。

## 2. スコープ
### 2.1 対象範囲（In Scope）
- 地域限定の介護事業所データを対象としたRAG基盤。
- チャットUIでの相談受付（例: 地域、サービス種別、希望条件）。
- 候補事業所の提示と根拠情報（データソース）表示。
- 不確実時の回答抑制（「不明」や「要確認」の明示）。

### 2.2 対象外（Out of Scope）
- 空き状況のリアルタイム照会。
- 事業所への自動連絡・予約代行。
- 地図アプリレベルの高度ルート案内。

### 2.3 前提条件
- 初期は1地域または1自治体に限定して検証する（仮説）。
- 事業所データを合法的に取得・更新できる運用体制がある（不明）。
- PoC期間は4〜8週間程度を想定（仮説）。

### 2.4 制約条件
- 個人情報の取り扱いを最小化し、相談文の保存ポリシーを定義する必要がある。
- 生成AI特有の誤回答リスクを前提に、出典表示と回答ガードレールが必須。
- データ鮮度が低い場合、推薦品質が急速に劣化する。

## 4. 要求一覧（ビジネス要求 / ユーザー要求 / システム要求）
| ID | 区分 | 要求内容 | 優先度 | 根拠 | 状態 |
|---|---|---|---|---|---|
| BR-001 | ビジネス | 相談者への初回候補提示までの時間を短縮する | Must | 現場工数削減（仮説） | 仮確定 |
| BR-002 | ビジネス | 候補提示時に根拠データを表示し説明責任を担保する | Must | 誤案内リスク低減 | 仮確定 |

| UR-002 | ユーザー | 候補ごとの差分（サービス/費用目安/連絡先）を比較したい | Should | 利便性向上（仮説） | 未確定 |
| SR-001 | システム | 事業所データを検索可能な形で保持しRAG参照できる | Must | 機能成立条件 | 仮確定 |
| SR-002 | システム | 根拠不足時は断定回答せず「不明/要確認」を返す | Must | 安全性担保 | 仮確定 |

優先度の目安:
- Must: ないと成立しない
- Should: 重要だが代替運用可能
- Could: あれば価値が増す
- Won't (今回): 今回は実施しない

## 5. 業務フロー / ユーザーストーリー
### 5.1 主要ユーザーストーリー
1. As a 介護相談者, I want 条件を会話で伝えて候補を受け取りたい, so that 探索時間を減らせる.
2. As a 相談担当者, I want 候補提示の根拠を確認したい, so that 説明品質を一定にできる.

### 5.2 受け入れ条件（Acceptance Criteria）
- [ ] Given 地域とサービス種別が入力されたとき When 回答生成する Then 条件に合う候補を複数返す。
- [ ] Given 根拠データが不足しているとき When 回答生成する Then 断定せず「不明」または確認先を返す。

### 7.3 セキュリティ

### 7.4 運用・保守

### 7.5 拡張性

## 11. 反論・代替案・懸念点（必須）
### 11.1 主要な反論
- 反論1: RAGチャットは誤回答時の影響が大きく、介護領域では信頼毀損が致命的。  
  影響: 誤案内、クレーム、運用停止。  
  反証/対応: 根拠表示、断定回避、有人窓口へのエスカレーション導線を必須化。
- 反論2: 自由文チャットより、構造化検索フォームの方が正確で速い可能性がある。  
  影響: LLM導入コストが過剰になる可能性。  
  反証/対応: PoCで「チャット方式 vs フォーム方式」の比較検証を実施。

### 11.2 代替案
- 代替案A: まずはLLMなしの条件検索UIを先行実装する。
  - メリット: 誤回答リスクが低く、説明性が高い。
  - デメリット: 自然文の利便性が低い。
  - 採否: 比較対象として採用（仮）。
- 代替案B: 検索はルールベース、説明文のみLLMで生成するハイブリッド方式。
  - メリット: 正確性と体験のバランスを取りやすい。
  - デメリット: 実装複雑性が増える。
  - 採否: 有力候補（仮）。

### 11.3 懸念点・リスク
| リスク | 発生確率 | 影響度 | 兆候 | 予防策 | 発生時対応 |
|---|---|---|---|---|---|
| データ更新遅延で古い情報を提示 | 中 | 高 | 問い合わせ不一致増加 | 更新SLA定義、更新監視 | 旧情報ラベル表示、即時更新 |
| 地域/条件解釈ミスで不適切候補を提示 | 中 | 高 | 再質問率上昇 | 条件確認ステップ追加 | 人手確認フローへ切替 |
| 個人情報取り扱いが未定義 | 中 | 高 | 保存ルール不統一 | 保存最小化、法務レビュー | ログ削除、運用停止判断 |
